## 1. System Architecture & Queue Mechanics

All emails generated by Swayam Admission (student registration OTPs, welcome emails, employee password reset links, admission updates, marketing announcements) are managed through a resilient, decoupled architecture:

```
[ Application Service ]
         │ (Transactional Enqueue)
         ▼
[ DurableOutboxService ] ──(PostgreSQL: CommunicationDelivery)
         │
         ├──► Pre-dispatch Validation (Suppression, TTL, Superseded)
         │
         ▼
[ EmailChannel ] ──(Transport: Amazon SES / SendGrid / Gmail)
         │
         ├──► Success: status = SENT (ProviderMsgId recorded)
         ├──► Hard Bounce / Complaint: Webhook updates status = BOUNCED
         └──► Rate Limit / Quota Exceeded: 15-Minute Cooldown Circuit Breaker
```

## 2. Quota & Provider Outage Incident Handling

### Scenario A: Google SMTP Daily Sending Limit Exceeded (`550-5.4.5`)

#### Symptoms
- Error logged: `Data command failed: 550-5.4.5 Daily user sending limit exceeded`.
- Channel health transitions to `BLOCKED`.
- Log: `[OUTBOX PROVIDER QUOTA EXCEEDED] Daily sending limit exceeded on email channel. Activating 15m cooldown...`

#### Immediate Automated Behavior
1. The system **does not** fail the pending messages permanently or burn retry counters.
2. The affected messages remain safely retained in PostgreSQL with `status: QUEUED`, `isRetryable: true`, and `failureReason: PROVIDER_QUOTA_EXCEEDED`.
3. In-memory circuit breaker activates a 15-minute cooldown (`emailQuotaCooldownUntil = Date.now() + 15m`).
4. During this cooldown, any incoming email dispatch attempts are automatically deferred rather than creating spam errors against the SMTP server.

#### Operational Remediation
1. **Option 1: Switch to Dedicated Relay (Permanent Solution):**
   - Follow `PHASE_6_EMAIL_PROVIDER_SETUP_GUIDE.md` to configure Amazon SES or SendGrid.
   - Set `EMAIL_PROVIDER=AMAZON_SES` and credentials in Render environment variables.
   - Trigger the admin cooldown reset endpoint to resume dispatch immediately:
     ```bash
     curl -X POST https://swayam-admission.onrender.com/v1/notifications/campaigns/outbox/reset-cooldown \
       -H "Authorization: Bearer <ADMIN_TOKEN>"
     ```
2. **Option 2: Wait for Rolling Quota Reset:**
   - Free Gmail SMTP quotas reset on a rolling 24-hour window from the first send of the batch.
   - After the 24-hour window, reset the cooldown and trigger retry:
     ```bash
     curl -X POST https://swayam-admission.onrender.com/v1/notifications/campaigns/outbox/retry-quota-blocked \
       -H "Authorization: Bearer <ADMIN_TOKEN>"
     ```

## 3. Webhook Delivery Event & Suppression Management

### 3.1 Hard Bounces & Spam Complaints
A hard bounce indicates a permanent failure (e.g., recipient address does not exist, domain is invalid, or mail server rejected the address permanently). A complaint indicates the recipient clicked "Report as Spam".

#### Automated Action
1. Provider webhook delivers bounce or complaint event to `/v1/notifications/webhook/:provider`.
2. `NotificationDispatcher` matches the delivery by `providerMessageId` or `recipientEmail`.
3. The delivery record status is updated to `BOUNCED` with `failureReason: HARD_BOUNCE` or `failureReason: COMPLAINT`.
4. **Automated Suppression:** `EmailChannel.send()` checks for existing `BOUNCED` records for that recipient before contacting SMTP. Any future send to that address is automatically short-circuited:
   - Status: `SKIPPED`
   - Log: `[EMAIL SUPPRESSION] Recipient <email> skipped dispatch due to prior HARD_BOUNCE / COMPLAINT`
   - Quota burned: 0. Sender reputation protected: 100%.

### 3.2 Idempotency & State Precedence
- If a provider sends duplicate callbacks for the same event, the webhook handler returns `idempotencySkipped: true` without performing redundant database writes.
- If a network delay causes an older event (`SENT`) to arrive after a terminal event (`DELIVERED` or `BOUNCED`), the handler rejects the regression (`outOfOrderIgnored: true`) and preserves the terminal state.

## 4. Safe Queue Recovery & Anti-Replay Rules

When recovering from an outage or quota block, bulk-replaying stale authentication messages is dangerous:

### 4.1 TTL Expiry Suppression
- Registration OTPs and email verifications have a strict Time-To-Live (TTL):
  - `REGISTRATION_OTP`: 10 minutes maximum age.
  - `EMAIL_VERIFICATION`: 20 minutes maximum age.
- When an outbox worker encounters a pending delivery older than its TTL, it automatically suppresses delivery:
  - Status: `FAILED`
  - Reason: `AUTH_MESSAGE_EXPIRED`
  - Result: Users are never surprised by outdated OTP codes.

### 4.2 Superseded Delivery Suppression
- If a user requested an OTP at 10:00 AM (Job 1) and requested another at 10:02 AM (Job 2):
  - Job 1 is superseded by Job 2.
  - The worker checks if a newer delivery exists for the same recipient and purpose.
  - Job 1 is marked `FAILED` with reason `SUPERSEDED_BY_NEWER_REQUEST`. Only Job 2 is dispatched.

## 5. Administrative Observability & Monitoring

### 5.1 Outbox Metrics API
Inspect queue health at any time:
```bash
curl -X GET https://swayam-admission.onrender.com/v1/notifications/campaigns/outbox-metrics \
  -H "Authorization: Bearer <ADMIN_TOKEN>"
```

**Response Format:**
```json
{
  "queueDepth": 3,
  "oldestQueuedAgeSeconds": 45,
  "stuckSendingCount": 0,
  "isQuotaCooldownActive": false,
  "quotaCooldownRemainingSeconds": 0,
  "last24hStats": {
    "total": 45,
    "sent": 38,
    "delivered": 36,
    "failed": 2,
    "bounced": 0
  }
}
```

### 5.2 Key Alerting Thresholds
| Metric | Normal Range | Warning Threshold | Critical Escalation |
|---|---|---|---|
| `queueDepth` | 0 – 20 | > 50 (for > 5 mins) | > 200 (investigate worker/transport) |
| `oldestQueuedAgeSeconds` | < 60s | > 300s (5 mins) | > 900s (15 mins) |
| `stuckSendingCount` | 0 | > 5 | > 10 (run crash recovery) |
| `isQuotaCooldownActive` | false | true (15m active) | true for > 2 hours |

## 6. Escalation & Diagnostic Procedures

### Step 1: Diagnose Transport Health
Test the active transport credentials without sending an email:
```bash
curl -X POST https://swayam-admission.onrender.com/v1/notifications/campaigns/test-email-connection \
  -H "Authorization: Bearer <ADMIN_TOKEN>"
```
- If `status: READY`: SMTP server is reachable and credentials are valid.
- If `status: FAILED`: Inspect error message (e.g. `Invalid login`, `ETIMEDOUT`, `Connection refused`).
- If `status: BLOCKED`: Check cooldown expiration in `outbox-metrics`.

### Step 2: Check Stale Workers
If messages are stuck in `status: SENDING`:
- Run worker crash recovery (handled automatically by `DurableOutboxService.recoverStaleSending()`).
- Stale `SENDING` jobs older than 5 minutes with no provider message ID are safely reverted to `QUEUED`.
- Jobs that have exceeded `maxRetries` (3) are marked `FAILED`.

### Step 3: Emergency Email Provider Swap
If the active provider (e.g., SES or SendGrid) experiences an outage:
1. Log into the Render dashboard.
2. Update `EMAIL_PROVIDER` and corresponding SMTP environment variables to the standby provider.
3. Save environment variables (Render will trigger a zero-downtime rolling redeploy).
4. Call `POST /v1/notifications/campaigns/outbox/reset-cooldown` to unfreeze the queue.
5. Pending messages in the durable outbox will immediately begin processing through the new provider.
